02

Les limites du RAG vectoriel face aux relations

Le RAG vectoriel est optimisé pour répondre à des questions dont la réponse se trouve dans un passage de texte — une information localisée. Il échoue dès qu'il faut traverser des relations entre plusieurs entités pour répondre.

Les questions que le RAG vectoriel ne peut pas traiter

ÉCHECS DU RAG VECTORIEL — QUESTIONS RELATIONNELLES ═════════════════════════════════════════════════════ Question 1 : "Quels fournisseurs travaillent avec des entreprises concurrentes de notre client X ?" → Nécessite : X → [concurrent_de] → Y → [fournisseur_de] → Z → RAG vectoriel : aucun passage ne contient cette chaîne de relations Question 2 : "Quels médicaments interagissent avec ceux que prend le patient Y ?" → Nécessite : Patient_Y → [prend] → [Méd_A, Méd_B] → [interagit_avec] → Méd_C → RAG vectoriel : les interactions sont dans des docs séparés Question 3 : "Quels employés ont travaillé sous le même manager que Marie ?" → Nécessite : Marie → [manage_par] → Manager_X → [manage] → {autres employés} → RAG vectoriel : la relation transitoire n'est pas dans un seul chunk Question 4 : "Comment XYZ Corp est-elle liée à la fraude détectée ?" → Nécessite : traverser plusieurs arêtes de relations → RAG vectoriel : impossible sans graphe structuré
La règle du pouce

Si la réponse à une question nécessite de suivre une chaîne de relations entre entités (A → B → C → D), le RAG vectoriel sera insuffisant. Si la réponse est contenue dans un passage de texte contigu, le RAG vectoriel est parfaitement adapté. GraphRAG est complémentaire, pas un remplaçant.

03

Graphes de connaissances

Un graphe de connaissances (Knowledge Graph) est une base de données structurée qui représente les entités du monde réel et les relations entre elles sous forme de graphe orienté.

Les éléments fondamentaux

⬤
Nœuds (Entités)
Représentent des objets réels : personnes, organisations, produits, concepts. Ex: "Marie Curie", "Université de Paris", "Prix Nobel".
→
Arêtes (Relations)
Représentent les liens entre entités, toujours typées et dirigées. Ex: [a_étudié_à], [a_reçu], [est_fondateur_de].
🏷️
Propriétés (Attributs)
Métadonnées sur les nœuds et arêtes. Ex: date_naissance="1867", année=1903, montant="150K SEK".
📐
Triplets (Faits)
La forme élémentaire : (Sujet, Prédicat, Objet). Ex: (Marie_Curie, a_reçu, Prix_Nobel_Physique_1903).

Graphe de connaissances interactif — Passez la souris sur les nœuds pour voir les détails

Langages de requête pour les graphes

🔍 Cypher (Neo4j) — Le SQL des graphes ▼
Cypher — Neo4j
// Trouver tous les concurrents des fournisseurs de notre client
MATCH (client:Company {name: "MonClient"})
      -[:HAS_SUPPLIER]->(fournisseur:Company)
      -[:WORKS_WITH]->(concurrent:Company)
      -[:COMPETES_WITH]->(client)
WHERE concurrent.name <> "MonClient"
RETURN fournisseur.name, concurrent.name, concurrent.revenue
ORDER BY concurrent.revenue DESC
LIMIT 10

Cypher est un langage déclaratif optimisé pour les parcours de graphe. La syntaxe visuelle (nœuds comme cercles, relations comme flèches) rend les requêtes très lisibles.

📊 SPARQL — Standard W3C pour les graphes RDF ▼

SPARQL est le langage de requête standard pour les graphes RDF (Resource Description Framework) — le format adopté par Wikidata, DBpedia, et les linked data. Syntaxe proche du SQL mais orientée triplets (Sujet, Prédicat, Objet).

SPARQL
# Trouver les Prix Nobel reçus par des chercheurs nés en Pologne
SELECT ?chercheur ?prix ?année
WHERE {
  ?chercheur dbo:birthPlace ?ville .
  ?ville dbo:country dbr:Poland .
  ?chercheur dbo:award ?prix .
  ?prix rdf:type dbo:NobelPrize .
  ?prix dbo:year ?année .
}
ORDER BY ?année

Architecture GraphRAG

GraphRAG est le terme générique pour les architectures qui combinent graphes de connaissances et LLMs. Il existe plusieurs patterns :

flowchart TD A["📄 Documents bruts"] --> B["🔍 Extraction d'entités\n& relations (NER + RE)"] B --> C["🕸️ Graphe de\nConnaissances"] C --> D["🗄️ Vector DB\n(embeddings des nœuds)"] A --> E["📝 Chunks textuels\n+ Vector DB classique"] F["❓ Question utilisateur"] --> G["🧠 Analyse de la question\n(entités détectées)"] G --> H["🔍 Cypher/SPARQL\nQuery Generation"] H --> C G --> I["🔢 Vector Search\nsur chunks"] I --> E C --> J["📋 Faits du graphe\n(triplets, chemins)"] E --> J J --> K["📝 Prompt augmenté\nGraphe + Texte"] K --> L["🤖 LLM → Réponse\nfidèle et relationnelle"] style C fill:#1a1e2a,stroke:#d946ef,color:#d946ef style L fill:rgba(217,70,239,.1),stroke:#d946ef,color:#e8eaf2

Les 3 patterns GraphRAG

📊
Graph-only RAG
Le LLM génère des requêtes Cypher/SPARQL. Les résultats du graphe sont directement injectés dans le prompt. Idéal pour les questions purement relationnelles.
🔀
Hybrid Graph+Vector
Combiner recherche vectorielle (pour la similarité sémantique) ET traversée de graphe (pour les relations). Les deux contextes sont fusionnés dans le prompt.
🌐
Graph-enhanced Retrieval
Enrichir les chunks avec des métadonnées de graphe (entités, relations) pour améliorer le filtering et le ranking du retrieval classique.
05

Extraction d'entités et de relations

La première étape de GraphRAG est de construire le graphe depuis les textes. On extrait automatiquement les entités (NER) et les relations entre elles (RE).

Pipeline d'extraction NER + RE avec LLM

Python — Extraction de triplets avec LLM
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
import json

extraction_prompt = ChatPromptTemplate.from_messages([("human", """
Extrais les entités et relations du texte suivant.
Retourne un JSON avec :
- entities: [{id, label, type, properties}]
- relations: [{source_id, target_id, type, properties}]

Types d'entités : PERSON, ORGANIZATION, LOCATION, CONCEPT, PRODUCT, DATE
Types de relations : WORKS_FOR, FOUNDED, LOCATED_IN, ACQUIRED, COMPETES_WITH, etc.

Texte : {text}

JSON uniquement :""")])

llm = ChatOpenAI(model="gpt-4o", temperature=0)

def extract_graph_elements(text: str) -> dict:
    response = (extraction_prompt | llm).invoke({"text": text})
    return json.loads(response.content)

# Exemple
text = """Marie Curie, physicienne polonaise, a fondé l'Institut du Radium
à Paris en 1914. Elle a travaillé en collaboration avec son mari
Pierre Curie, également physicien. Ensemble, ils ont découvert
le polonium et le radium."""

result = extract_graph_elements(text)
# Résultat :
# entities: [
#   {id: "marie_curie", label: "Marie Curie", type: "PERSON"},
#   {id: "pierre_curie", label: "Pierre Curie", type: "PERSON"},
#   {id: "inst_radium", label: "Institut du Radium", type: "ORGANIZATION"},
#   {id: "polonium", label: "Polonium", type: "CONCEPT"},
#   {id: "radium", label: "Radium", type: "CONCEPT"}
# ]
# relations: [
#   {source: "marie_curie", target: "inst_radium", type: "FOUNDED", properties: {year: 1914}},
#   {source: "marie_curie", target: "pierre_curie", type: "MARRIED_TO"},
#   {source: "marie_curie", target: "polonium", type: "DISCOVERED"},
#   {source: "marie_curie", target: "radium", type: "DISCOVERED"}
# ]

Insertion dans Neo4j

Python — Ingestion dans Neo4j
from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "password"))

def ingest_to_neo4j(entities, relations):
    with driver.session() as session:
        # Créer les nœuds
        for entity in entities:
            session.run(
                f"MERGE (n:{entity['type']} {{id: $id}}) SET n.label = $label",
                id=entity["id"], label=entity["label"]
            )
        # Créer les relations
        for rel in relations:
            query = f"""
            MATCH (a {{id: $src}}), (b {{id: $tgt}})
            MERGE (a)-[r:{rel['type']}]->(b)
            SET r += $props
            """
            session.run(query, src=rel["source"], tgt=rel["target"],
                       props=rel.get("properties", {}))

GraphRAG Microsoft — L'approche globale

Microsoft Research a publié GraphRAG (Edge et al., 2024) — une approche radicalement différente qui génère d'abord un graphe de connaissances hiérarchique, puis permet des requêtes globales sur l'ensemble du corpus.

MICROSOFT GRAPHRAG — DEUX MODES DE REQUÊTE ════════════════════════════════════════════ CONSTRUCTION DU GRAPHE (Offline) : 1. Extraction d'entités et relations depuis tous les documents 2. Détection de communautés (clusters d'entités fortement connectées) → Algorithme : Leiden Community Detection 3. Génération de "community summaries" par niveau Level 0 : résumé des petits clusters locaux Level 1 : résumé des clusters de niveau supérieur Level 2 : vue globale du corpus MODE 1 — LOCAL SEARCH (questions spécifiques) : "Qui est Marie Curie ?" → Récupère les nœuds et relations proches de "Marie Curie" → + Chunks textuels liés à ces entités → Réponse précise et contextualisée MODE 2 — GLOBAL SEARCH (questions analytiques larges) : "Quelles sont les grandes tendances de la recherche en physique ?" → Utilise les community summaries (pas la recherche vectorielle) → Agrège les insights de plusieurs communautés → Map-Reduce sur les summaries → Réponse globale AVANTAGE UNIQUE : GraphRAG peut répondre à des questions analytiques sur l'ENSEMBLE du corpus — impossible avec le RAG vectoriel classique.
Quand utiliser Microsoft GraphRAG ?

GraphRAG brille sur les questions globales ("Quels sont les thèmes principaux de toute cette documentation ?") et les analyses comparatives cross-documents. Son coût d'indexation est élevé (beaucoup d'appels LLM pour générer les summaries) mais la qualité sur les questions analytiques est bien supérieure au RAG classique.

Python — Microsoft GraphRAG (CLI)
# Installation
# pip install graphrag

# Initialisation du projet
# graphrag init --root ./graphrag_project

# Indexation (extraction + communautés + summaries)
# graphrag index --root ./graphrag_project

# Requête en Python
from graphrag.query.cli import run_global_search, run_local_search

# Recherche locale (entités spécifiques)
result = run_local_search(
    root_dir="./graphrag_project",
    query="Quelles sont les découvertes de Marie Curie ?"
)

# Recherche globale (analytique, sur tout le corpus)
result = run_global_search(
    root_dir="./graphrag_project",
    query="Quels sont les grands thèmes de ce corpus ?"
)

Neo4j + RAG — L'approche Text2Cypher

L'approche Text2Cypher permet au LLM de générer automatiquement des requêtes Cypher depuis du langage naturel. C'est l'équivalent de Text2SQL pour les graphes.

Python — Text2Cypher avec LangChain + Neo4j
from langchain_community.graphs import Neo4jGraph
from langchain.chains import GraphCypherQAChain
from langchain_openai import ChatOpenAI

# Connexion Neo4j
graph = Neo4jGraph(
    url="bolt://localhost:7687",
    username="neo4j",
    password="password"
)

# Afficher le schéma (pour que le LLM comprenne la structure)
print(graph.schema)
# Node properties: {Company: {name, revenue, industry}, Person: {name, title}...}
# Relationships: (Company)-[:COMPETES_WITH]->(Company), (Person)-[:WORKS_FOR]->(Company)

# Chaîne Text2Cypher
chain = GraphCypherQAChain.from_llm(
    llm=ChatOpenAI(model="gpt-4o", temperature=0),
    graph=graph,
    verbose=True,
    return_intermediate_steps=True
)

result = chain.invoke({
    "query": "Quels fournisseurs travaillent avec des concurrents de TechCorp ?"
})

# Le LLM génère automatiquement :
# MATCH (tc:Company {name: "TechCorp"})
#       <-[:COMPETES_WITH]-(concurrent)
#       <-[:SUPPLIES]-(fournisseur)
# RETURN fournisseur.name, concurrent.name
print(result["result"])

Raisonnement Multi-hop

Le raisonnement multi-hop consiste à enchaîner plusieurs étapes de recherche dans le graphe pour répondre à une question. C'est l'une des capacités les plus puissantes de GraphRAG.

RAISONNEMENT MULTI-HOP — EXEMPLE MÉDICAL ══════════════════════════════════════════ GRAPHE DE CONNAISSANCES MÉDICAL : (Patient_X) -[prend]-> (Warfarine) (Patient_X) -[prend]-> (Ibuprofène) (Warfarine) -[interagit_avec]-> (Ibuprofène) [type: SÉVÈRE, mécanisme: anticoagulation] (Warfarine) -[traite]-> (Thrombose_veineuse) (Ibuprofène) -[inhibe]-> (COX1_COX2) QUESTION : "Le patient X présente-t-il des risques d'interaction médicamenteuse ?" TRAVERSÉE DU GRAPHE (multi-hop) : Hop 1 : Patient_X → [prend] → {Warfarine, Ibuprofène} Hop 2 : Warfarine → [interagit_avec] → Ibuprofène ← [prend] ← Patient_X → Interaction détectée : Warfarine ↔ Ibuprofène (SÉVÈRE) Hop 3 (contexte) : Warfarine → [traite] → Thrombose_veineuse Hop 4 (mécanisme) : Ibuprofène → [inhibe] → COX1_COX2 Warfarine ← [potentiel_augmenté_par] ← Inhibition_COX CYPHER QUERY GÉNÉRÉE : MATCH (p:Patient {id: "X"})-[:TAKES]->(m1:Drug) MATCH (p)-[:TAKES]->(m2:Drug) MATCH (m1)-[i:INTERACTS_WITH]->(m2) RETURN m1.name, m2.name, i.severity, i.mechanism RÉSULTAT → CONTEXTE POUR LE LLM : "Warfarine et Ibuprofène : interaction SÉVÈRE. L'ibuprofène potentialise l'effet anticoagulant de la warfarine par inhibition COX, risque hémorragique élevé."

Hybrid Graph + Vector RAG

La combinaison la plus puissante : recherche vectorielle pour la similarité sémantique + traversée de graphe pour les relations. Les deux sources d'information sont fusionnées dans le prompt.

Python — Hybrid GraphRAG
from langchain_community.graphs import Neo4jGraph
from langchain_community.vectorstores import Neo4jVector
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# Neo4j Vector Store (stocke embeddings sur les nœuds)
neo4j_vector = Neo4jVector.from_existing_index(
    embedding=OpenAIEmbeddings(),
    index_name="document_embeddings"
)

graph = Neo4jGraph()
llm = ChatOpenAI(model="gpt-4o")

def hybrid_graph_rag(question: str) -> str:
    # 1. Recherche vectorielle sur les nœuds
    vector_docs = neo4j_vector.similarity_search(question, k=3)
    
    # 2. Extraire les entités de la question
    entities = extract_entities_from_question(question, llm)
    
    # 3. Traversée du graphe depuis ces entités
    graph_facts = []
    for entity in entities:
        cypher = f"""
        MATCH (n {{name: '{entity}'}})-[r]-(m)
        RETURN n.name, type(r), m.name, m.type
        LIMIT 20
        """
        results = graph.query(cypher)
        graph_facts.extend(results)
    
    # 4. Combiner les deux sources
    prompt = ChatPromptTemplate.from_messages([("human", """
Réponds à la question en utilisant les deux sources d'information :

FAITS DU GRAPHE DE CONNAISSANCES :
{graph_facts}

PASSAGES TEXTUELS PERTINENTS :
{vector_context}

Question : {question}
""")])
    
    chain = prompt | llm | StrOutputParser()
    return chain.invoke({
        "graph_facts": str(graph_facts),
        "vector_context": "\n".join(d.page_content for d in vector_docs),
        "question": question
    })

La recommandation pragmatique

Pour 80% des cas d'usage RAG, le RAG vectoriel classique suffit. Adoptez GraphRAG uniquement si (1) vous avez des questions multi-hop fréquentes, (2) vous avez des relations complexes entre entités à modéliser, ou (3) vous avez besoin d'analyses globales du corpus. Le coût de construction et maintenance du graphe est significatif.

Erreurs fréquentes

❌ Erreur 1 — Construire un graphe sans schéma préalable▼

Laisser le LLM inventer librement les types de nœuds et relations produit un graphe incohérent. Définir d'abord un ontologie : quels types d'entités (PERSON, COMPANY, DRUG…), quels types de relations (WORKS_FOR, INTERACTS_WITH…). Le schéma guide l'extraction et garantit la cohérence.

❌ Erreur 2 — Utiliser GraphRAG pour tout▼

GraphRAG est excellent pour les questions relationnelles mais plus lourd que le RAG vectoriel pour les questions factuelles simples. Ne pas remplacer le RAG vectoriel par GraphRAG — les combiner intelligemment selon le type de question détecté.

❌ Erreur 3 — Ne pas valider les triplets extraits▼

L'extraction automatique de relations par LLM produit des erreurs : relations incorrectes, entités mal typées, doublets. Toujours valider un échantillon des triplets extraits avant ingestion massive. Considérer une étape de "graph cleaning" pour supprimer les relations à faible confiance.

❌ Erreur 4 — Requêtes Cypher trop complexes pour le LLM▼

Le Text2Cypher fonctionne bien pour des requêtes simples à modérées. Pour des traversées très complexes (5+ hops, conditions multiples), le LLM peut générer du Cypher syntaxiquement invalide ou logiquement incorrect. Ajouter une étape de validation Cypher et de fallback vers une recherche vectorielle si la requête graphe échoue.

Nœuds :
• Metformine (DRUG)
• Diabète_Type_2 (DISEASE)

• (Metformine) -[TREATS]-> (Diabète_Type_2)

MoyenExercice 2 — Écrire une requête Cypher multi-hop
Dans un graphe de connaissances RH, vous avez les relations :
(Person)-[:MANAGES]->(Person), (Person)-[:WORKS_IN]->(Department), (Department)-[:PART_OF]->(Division)

Écrivez une requête Cypher qui répond à : "Quels sont tous les employés qui travaillent dans la division 'R&D', directement ou dans un département qui en fait partie ?" 
MATCH (d:Division {name: "R&D"})
MATCH (dept:Department)-[:PART_OF]->(d)
MATCH (person:Person)-[:WORKS_IN]->(dept)

ORDER BY dept.name, person.name
Variante plus concise avec path variable :
MATCH (person:Person)-[:WORKS_IN]->(dept:Department)-[:PART_OF]->(d:Division {name: "R&D"})
RETURN person.name, dept.name
DifficileExercice 3 — Concevoir un Hybrid GraphRAG
Vous construisez un assistant RAG pour une équipe de cybersécurité. La base de connaissances contient :
• Des rapports d'incidents (texte libre, 500 documents)
• Un graphe de connaissances MITRE ATT&CK (techniques, tactiques, acteurs de menace)

Question type : "Est-ce que l'attaque détectée (exfiltration via DNS) ressemble aux TTPs du groupe APT41 ?"

a) Décrivez l'architecture Hybrid GraphRAG pour ce cas d'usage.
b) Quelles entités et relations modéliseriez-vous dans le graphe ?
c) Comment routez-vous entre recherche vectorielle et graphe selon la question ?
a) Architecture :
Phase 1 (question analysis) : LLM identifie les entités cybersécurité dans la question (APT41, DNS exfiltration, TTPs). Classifie le type de requête : "attribution" → graphe, "description d'incident" → vectoriel, "les deux" → hybride.
Phase 2 (parallèle) : Vector search sur les rapports d'incidents ("exfiltration DNS") + Cypher sur le graphe ATT&CK (APT41 → [uses] → Techniques).
Phase 3 (fusion) : Combiner les techniques ATT&CK de APT41 (graphe) avec les incidents similaires (vectoriel) dans le prompt.

b) Entités & relations :
Nœuds : ThreatActor (APT41), Tactic (Exfiltration), Technique (T1048 - Exfil via DNS), Tool (DNScat2), Target (secteur, pays)
Relations : (APT41)-[:USES]->(T1048), (T1048)-[:PART_OF]->(Exfiltration), (T1048)-[:IMPLEMENTED_BY]->(DNScat2)

c) Routing :
Détection de patterns : présence d'un acteur nommé (APT41) → graphe. Présence d'une technique spécifique (T1048) → graphe + vectoriel. Question descriptive sans entité connue → vectoriel pur. Question d'attribution → graphe prioritaire + enrichissement vectoriel.

Quiz d'auto-évaluation

Q1. Pour quelle type de question GraphRAG surpasse-t-il le RAG vectoriel ?
A) Questions factuelles dans un passage de texte
B) Questions nécessitant de suivre une chaîne de relations entre entités
C) Questions sur des documents PDF scannés
D) Questions en langue étrangère
GraphRAG brille sur les questions multi-hop relationnelles ("Quels fournisseurs de X travaillent avec des concurrents de Y ?") car il peut traverser des relations dans le graphe. Le RAG vectoriel ne peut pas naviguer des relations structurées entre entités.
Q2. Qu'est-ce qu'un triplet dans un graphe de connaissances ?
A) Trois documents associés à une même requête
B) Un fait élémentaire de la forme (Sujet, Prédicat, Objet)
C) Une requête Cypher avec trois conditions
D) Un nœud connecté à exactement trois autres nœuds
Un triplet est la forme atomique d'un fait dans un graphe de connaissances : (Marie_Curie, a_reçu, Prix_Nobel_Physique). Sujet = entité source, Prédicat = type de relation, Objet = entité cible.
Q3. Quelle est la caractéristique unique du "Global Search" de Microsoft GraphRAG ?
A) Il peut répondre à des questions analytiques sur l'ensemble du corpus via des community summaries
B) Il recherche uniquement dans des graphes SQL
C) Il utilise uniquement des embeddings vectoriels
D) Il ne nécessite pas de LLM pour fonctionner
Le Global Search de Microsoft GraphRAG génère des "community summaries" qui condensent les insights de clusters d'entités. Cela permet de répondre à des questions analytiques globales ("Quels sont les grands thèmes de ce corpus ?") — quelque chose d'impossible avec le RAG vectoriel classique.
Q4. Qu'est-ce que l'approche Text2Cypher ?
A) Convertir des fichiers texte en base Neo4j
B) Générer automatiquement des requêtes Cypher depuis du langage naturel via LLM
C) Extraire du texte depuis les nœuds d'un graphe
D) Convertir des requêtes SQL en Cypher
Text2Cypher (analogue à Text2SQL) utilise un LLM pour traduire une question en langage naturel en requête Cypher pour Neo4j. Le LLM reçoit le schéma du graphe et génère la requête appropriée automatiquement.

🎯 Ce qu'il faut absolument retenir

1
Le RAG vectoriel échoue sur les questions relationnelles multi-hop. GraphRAG comble cette lacune en traversant des relations structurées.
2
Un graphe de connaissances représente les entités (nœuds) et leurs relations (arêtes) sous forme de triplets (Sujet, Prédicat, Objet).
3
Microsoft GraphRAG crée des community summaries qui permettent des requêtes analytiques globales sur tout le corpus — unique capacité.
4
Text2Cypher permet au LLM de générer des requêtes Neo4j depuis du langage naturel en connaissant le schéma du graphe.
5
L'Hybrid GraphRAG combine recherche vectorielle (similarité sémantique) ET traversée de graphe (relations) — pattern optimal en production.
6
Adopter GraphRAG uniquement si vous avez des relations complexes à modéliser. Le coût de construction et maintenance du graphe est significatif.
