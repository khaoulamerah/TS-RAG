02

Pourquoi l'évaluation RAG est non triviale

Évaluer un système RAG est bien plus difficile qu'évaluer un classificateur standard. Il n'existe pas de simple métrique accuracy ou F1 — la qualité d'une réponse en langage naturel est multidimensionnelle et subjective.

Les dimensions de la qualité RAG

✅
Fidélité (Faithfulness)
La réponse est-elle supportée par les documents récupérés ? Pas d'information inventée ?
🎯
Pertinence de la réponse
La réponse répond-elle réellement à la question posée ?
📋
Recall du contexte
A-t-on récupéré tous les documents nécessaires pour répondre ?
🔍
Précision du contexte
Les documents récupérés sont-ils tous pertinents ? Pas de bruit ?
Le triangle de l'évaluation RAG

Un système RAG peut avoir une haute fidélité mais une faible pertinence (répond fidèlement aux documents mais pas à la question). Il peut avoir un bon recall de contexte mais une faible précision (récupère les bons docs + beaucoup de mauvais). Chaque dimension doit être évaluée indépendamment pour un diagnostic précis.

Pourquoi l'évaluation humaine seule ne suffit pas

L'évaluation humaine est le gold standard mais elle est :

  • Coûteuse — un annotateur humain peut évaluer ~50-100 réponses/heure
  • Lente — impossible d'évaluer chaque déploiement en continu
  • Subjective — accord inter-annotateurs rarement >80% sur les nuances
  • Non scalable — un corpus de 10 000 questions nécessite des semaines

D'où l'émergence de l'approche LLM-as-Judge : utiliser un LLM puissant (GPT-4, Claude) pour automatiser l'évaluation, avec une corrélation élevée avec le jugement humain.

03

RAGAS — Les 4 métriques fondamentales

RAGAS (Retrieval-Augmented Generation Assessment, Es et al. 2023) est le framework d'évaluation RAG le plus adopté. Il propose 4 métriques qui couvrent les deux étapes clés : retrieval et génération.

INPUTS REQUIS PAR RAGAS ═════════════════════════ Pour calculer les 4 métriques, RAGAS nécessite : question : "Combien de jours de congés après 3 ans ?" answer : "Après 3 ans d'ancienneté, vous bénéficiez de 28 jours." contexts : ["Après 3 ans d'ancienneté, 28 jours...", "Tout salarié bénéficie..."] ground_truth : "Après 3 ans d'ancienneté, 28 jours ouvrés sont accordés." ┌─────────────────────────────┐ faithfulness │ answer + contexts │ → Pas de ground_truth requis answer_relevance │ question + answer │ → Pas de ground_truth requis context_recall │ contexts + ground_truth │ → Ground_truth requis context_precision │ question + contexts + gt │ → Ground_truth requis
04

Faithfulness — Fidélité aux sources

✅

Faithfulness

Mesure : la réponse ne contient-elle que des informations supportées par le contexte récupéré ?

La Faithfulness est la métrique anti-hallucination du RAG. Elle mesure quelle proportion des affirmations dans la réponse peut être directement attribuée aux documents fournis en contexte.

Faithfulness
Faithfulness = |Affirmations supportées par le contexte| / |Total des affirmations dans la réponse|

Plage : [0, 1] | 1.0 = toutes les affirmations sont dans les sources | 0.0 = hallucination totale
EXEMPLE DE CALCUL — FAITHFULNESS ══════════════════════════════════ CONTEXTE RÉCUPÉRÉ : [Doc 1] : "Après 3 ans d'ancienneté, le salarié bénéficie de 28 jours." [Doc 2] : "Les demandes doivent être soumises 15 jours à l'avance." RÉPONSE DU LLM : "Après 3 ans d'ancienneté, vous avez droit à 28 jours de congés payés. La demande doit être effectuée 15 jours à l'avance sur l'intranet. Vous pouvez également convertir 5 jours en RTT." DÉCOMPOSITION EN AFFIRMATIONS : Affirmation 1 : "Après 3 ans → 28 jours de congés" ← SUPPORTÉE ✅ (Doc 1) Affirmation 2 : "Demande 15 jours à l'avance" ← SUPPORTÉE ✅ (Doc 2) Affirmation 3 : "Convertir 5 jours en RTT" ← NON SUPPORTÉE ❌ (inventée !) FAITHFULNESS = 2/3 = 0.67 → La réponse contient une hallucination : la conversion en RTT n'est pas dans les documents fournis.

Comment RAGAS calcule la Faithfulness

RAGAS utilise un LLM-as-Judge en deux étapes :

  1. Extraction des affirmations : le LLM décompose la réponse en assertions atomiques
  2. Vérification NLI : pour chaque assertion, le LLM vérifie si elle peut être déduite du contexte (NLI = Natural Language Inference)
Python — RAGAS Faithfulness
from ragas.metrics import Faithfulness
from ragas import evaluate
from datasets import Dataset
from ragas.llms import LangchainLLMWrapper
from langchain_openai import ChatOpenAI

# Préparer les données
data = {
    "question": ["Combien de jours après 3 ans ?"],
    "answer": ["Après 3 ans, vous avez droit à 28 jours. Vous pouvez aussi convertir 5 jours en RTT."],
    "contexts": [["Après 3 ans d'ancienneté, 28 jours sont accordés.",
                   "Les demandes doivent être faites 15 jours à l'avance."]],
    "ground_truth": ["Après 3 ans, 28 jours sont accordés."]
}
dataset = Dataset.from_dict(data)

# LLM évaluateur
evaluator_llm = LangchainLLMWrapper(ChatOpenAI(model="gpt-4o"))

# Évaluer
result = evaluate(
    dataset,
    metrics=[Faithfulness()],
    llm=evaluator_llm
)
print(result)  # {'faithfulness': 0.67}

Answer Relevance — Pertinence de la réponse

🎯

Answer Relevance

Mesure : la réponse répond-elle directement à la question posée ?

Une réponse peut être fidèle aux sources (Faithfulness élevée) mais ne pas répondre à la question. Exemple : "Combien de congés après 5 ans ?" → "La politique de congés de notre entreprise remonte à 1985 et a été révisée plusieurs fois..." — fidèle si c'est dans les docs, mais hors-sujet.

L'approche de RAGAS : génération de questions inverses

Au lieu de comparer directement réponse et question, RAGAS génère N questions auxquelles la réponse pourrait répondre, puis mesure la similarité vectorielle entre ces questions générées et la question originale.

Answer Relevance
AR = (1/N) × Σᵢ cos(embedding(qᵢ_générée), embedding(question_originale))

qᵢ_générée = ième question générée par LLM depuis la réponse
Plage : [0, 1] | 1.0 = réponse parfaitement pertinente
EXEMPLE — ANSWER RELEVANCE ══════════════════════════ QUESTION ORIGINALE : "Combien de jours de congés après 3 ans ?" RÉPONSE DU LLM : "Après 3 ans d'ancienneté, vous bénéficiez de 28 jours ouvrés de congés payés par an." QUESTIONS GÉNÉRÉES PAR LE LLM depuis la réponse : Q1 : "Quel est le nombre de jours de congés pour 3 ans d'ancienneté ?" Q2 : "Combien de jours après 3 ans dans l'entreprise ?" Q3 : "Quel est le droit aux congés après 3 ans ?" SIMILARITÉ COSINUS avec la question originale : sim(Q1, originale) = 0.94 sim(Q2, originale) = 0.91 sim(Q3, originale) = 0.89 ANSWER RELEVANCE = (0.94 + 0.91 + 0.89) / 3 = 0.91 → La réponse est très pertinente pour la question. CAS MAUVAIS : réponse hors-sujet "La politique de congés est en vigueur depuis 1985..." Questions générées : "Depuis quand la politique de congés existe-t-elle ?" sim avec originale → 0.21 → Answer Relevance = 0.21 (très bas !)
06

Context Recall — Couverture du retrieval

📋

Context Recall

Mesure : a-t-on récupéré tous les documents nécessaires pour répondre correctement ?

Le Context Recall mesure si le contexte récupéré couvre l'ensemble des informations nécessaires pour produire la réponse de référence (ground truth). Nécessite un ground truth.

Context Recall
CR = |Phrases du ground_truth supportées par le contexte| / |Total des phrases du ground_truth|

Plage : [0, 1] | 1.0 = contexte couvre toute la réponse de référence | 0.0 = contexte inutile
EXEMPLE — CONTEXT RECALL ═════════════════════════ GROUND TRUTH (réponse de référence annotée) : "Après 3 ans d'ancienneté, le salarié bénéficie de 28 jours de congés payés. Les demandes doivent être faites 15 jours à l'avance. Les congés non pris au 31 décembre sont reportés dans la limite de 10 jours." DÉCOMPOSITION EN PHRASES (3 affirmations) : GT-1 : "Après 3 ans → 28 jours" GT-2 : "Demandes 15 jours à l'avance" GT-3 : "Report limité à 10 jours" CONTEXTE RÉCUPÉRÉ : [Doc 1] : "Après 3 ans d'ancienneté, 28 jours." → couvre GT-1 ✅ [Doc 2] : "Demandes 15 jours à l'avance." → couvre GT-2 ✅ ⚠️ GT-3 non couverte (Doc sur le report n'a pas été récupéré) CONTEXT RECALL = 2/3 = 0.67 DIAGNOSTIC : Le retrieval a raté le chunk sur le report des congés. → Problème de chunking ou de qualité d'embedding sur ce sujet.
Context Recall vs Recall@K

La différence est subtile mais importante. Le Recall@K (chapitre 5) mesure si le chunk exact est dans le Top-K. Le Context Recall RAGAS mesure si les informations nécessaires sont présentes dans le contexte injecté, indépendamment de quel chunk les contient. Context Recall est plus flexible et aligné avec ce qui compte vraiment : le LLM a-t-il accès à l'information ?

07

Context Precision — Signal vs Bruit

🔍

Context Precision

Mesure : les documents récupérés sont-ils tous pertinents ? (rapport signal/bruit)

Le Context Precision mesure si les chunks retournés sont majoritairement pertinents ou si le retrieval ramène trop de bruit. Un contexte avec beaucoup de documents non pertinents perturbe le LLM (Lost in the Middle) et dilue l'information utile.

Context Precision@K (variante pondérée)
CP@K = Σₖ (Precision@k × rel(k)) / |{docs pertinents dans Top-K}|

rel(k) = 1 si doc k est pertinent, 0 sinon | Precision@k = proportion de docs pertinents parmi les k premiers
EXEMPLE — CONTEXT PRECISION@5 ══════════════════════════════ Question : "Combien de jours de congés après 3 ans ?" Top-5 documents retournés (dans l'ordre) : Rang 1 : "Après 3 ans d'ancienneté, 28 jours..." → PERTINENT (rel=1) ✅ Rang 2 : "Budget marketing Q3 2024..." → NON PERTINENT (rel=0) ❌ Rang 3 : "Les demandes se font sur l'intranet..." → PERTINENT (rel=1) ✅ Rang 4 : "Règles de télétravail..." → NON PERTINENT (rel=0) ❌ Rang 5 : "Report des congés non pris..." → PERTINENT (rel=1) ✅ Precision@1 = 1/1 = 1.00 (rang 1 est pertinent) Precision@3 = 2/3 = 0.67 (2 pertinents sur 3 premiers) Precision@5 = 3/5 = 0.60 Context Precision (pondérée) : = (1.00×1 + 0×0 + 0.67×1 + 0×0 + 0.60×1) / 3 = (1.00 + 0.67 + 0.60) / 3 = 0.76 PROBLÈME IDENTIFIÉ : Des documents non pertinents (rang 2 et 4) "polluent" le contexte. → Le retrieval ramène du bruit qui peut perturber le LLM.

LLM-as-Judge — L'évaluateur automatique

Le paradigme LLM-as-Judge utilise un LLM puissant (GPT-4, Claude 3 Opus) pour évaluer automatiquement les sorties d'un autre LLM. Cette approche montre une corrélation de 80-90% avec le jugement humain expert.

Architecture d'un LLM-as-Judge

LLM-AS-JUDGE — PIPELINE D'ÉVALUATION ══════════════════════════════════════ INPUTS : question : "Combien de jours de congés après 3 ans ?" réponse : "Vous avez droit à 28 jours après 3 ans..." contexte : ["Après 3 ans, 28 jours sont accordés..."] ground_truth: "28 jours après 3 ans d'ancienneté" PROMPT DU JUGE (example pour Faithfulness) : ┌─────────────────────────────────────────────────────────────────┐ │ SYSTEM : Tu es un expert en évaluation de systèmes RAG. │ │ Évalue si la réponse est fidèle au contexte fourni. │ │ │ │ CONTEXTE : [Doc 1] : "Après 3 ans → 28 jours." │ │ │ │ RÉPONSE À ÉVALUER : "Vous avez droit à 28 jours après 3 ans." │ │ │ │ TÂCHE : │ │ 1. Décompose la réponse en affirmations atomiques │ │ 2. Pour chaque affirmation, détermine si elle est supportée │ │ par le contexte (oui/non) │ │ 3. Retourne un JSON {"faithfulness_score": 0.0-1.0} │ └─────────────────────────────────────────────────────────────────┘ OUTPUT DU JUGE : { "statements": ["Vous avez droit à 28 jours", "après 3 ans"], "supported": [true, true], "faithfulness_score": 1.0 }

Les biais du LLM-as-Judge

⚠️ Biais de verbosité — les réponses longues semblent meilleures ▼

Les LLMs-juges ont tendance à préférer les réponses longues et détaillées aux réponses courtes et précises, même quand la réponse courte est correcte. Contre-mesure : évaluer explicitement la concision ou utiliser des critères standardisés qui pénalisent la verbosité inutile.

⚠️ Biais de position — le premier élément présenté semble meilleur ▼

Dans les comparaisons A/B, le LLM-juge préfère souvent le premier élément présenté. Contre-mesure : inverser l'ordre de présentation et moyenner les deux évaluations.

⚠️ Self-enhancement bias — le LLM préfère ses propres sorties ▼

GPT-4-as-Judge peut favoriser les réponses générées par GPT-4 vs Claude ou LLaMA. Contre-mesure : utiliser un modèle différent pour l'évaluation que celui utilisé pour la génération. Idéalement : utiliser plusieurs juges et moyenner.

Calibration : corrélation LLM-Judge vs humain

Corrélations observées en pratique

• GPT-4-as-Judge vs human : corrélation de Spearman ~0.85 sur des tâches de pertinence
• Claude 3 Opus-as-Judge : résultats similaires avec moins de verbosité bias
• Faithfulness (RAGAS) : corrélation ~0.88 avec annotations humaines
• Answer Relevance : corrélation ~0.82 avec annotations humaines

Ces corrélations sont suffisantes pour l'évaluation automatique continue, tout en réservant l'évaluation humaine pour les cas ambigus et la calibration initiale.

Créer un dataset d'évaluation

Un bon dataset d'évaluation est la fondation de tout l'écosystème d'évaluation. Il représente l'investissement le plus important — mais aussi le plus rentable.

Les 3 approches de création

✍️ Approche 1 — Annotation manuelle (Gold Standard) ▼

Comment : Des experts du domaine créent des questions et leurs réponses de référence à partir des documents. Chaque paire est validée par au moins 2 annotateurs.

Avantages : Qualité maximale, représentativité réelle des questions utilisateurs.

Inconvénients : Lent (2-3h pour 50 paires), coûteux, difficile à mettre à jour.

Recommandation : Créer 50-200 paires Gold Standard. C'est le jeu de test principal, jamais modifié.

🤖 Approche 2 — Génération automatique (Synthetic) ▼

Utiliser un LLM pour générer automatiquement des questions à partir des documents. RAGAS propose TestsetGenerator qui génère des questions de différents niveaux de complexité.

Python — Génération automatique avec RAGAS TestsetGenerator
from ragas.testset.generator import TestsetGenerator
from ragas.testset.evolutions import simple, reasoning, multi_context
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.document_loaders import DirectoryLoader

# Charger les documents
loader = DirectoryLoader("./docs", glob="**/*.pdf")
documents = loader.load()

# Générateur de testset
generator = TestsetGenerator.from_langchain(
    generator_llm=ChatOpenAI(model="gpt-4o"),
    critic_llm=ChatOpenAI(model="gpt-4o-mini"),
    embeddings=OpenAIEmbeddings()
)

# Générer 100 questions avec distribution de complexité
testset = generator.generate_with_langchain_docs(
    documents,
    test_size=100,
    distributions={
        simple: 0.5,       # 50% questions simples
        reasoning: 0.25,   # 25% questions de raisonnement
        multi_context: 0.25  # 25% multi-documents
    }
)

testset.to_pandas().to_csv("eval_dataset.csv", index=False)
📊 Approche 3 — Mining des logs utilisateurs ▼

En production, les vraies questions des utilisateurs sont la source d'évaluation la plus réaliste. Collecter les interactions avec feedback utilisateur (thumbs up/down, réponses corrigées), puis annoter les cas représentatifs comme dataset de test.

Avantage : Distribution réelle des questions utilisateurs — ce qui compte vraiment.

Attention : Gérer la confidentialité et l'anonymisation des données utilisateurs.

Implémentation : CI/CD pour RAG

Python — Pipeline d'évaluation automatique (CI/CD)
import pandas as pd
from ragas import evaluate
from ragas.metrics import Faithfulness, AnswerRelevancy, ContextRecall, ContextPrecision
from datasets import Dataset

class RAGEvaluationPipeline:
    def __init__(self, rag_system, eval_dataset_path, thresholds):
        self.rag = rag_system
        self.eval_df = pd.read_csv(eval_dataset_path)
        self.thresholds = thresholds  # ex: {"faithfulness": 0.8, "answer_relevancy": 0.75}
        self.metrics = [Faithfulness(), AnswerRelevancy(), ContextRecall(), ContextPrecision()]
    
    def run(self) -> dict:
        # 1. Générer les réponses avec le système RAG actuel
        results = []
        for _, row in self.eval_df.iterrows():
            answer, contexts = self.rag.query(row["question"])
            results.append({
                "question": row["question"],
                "answer": answer,
                "contexts": contexts,
                "ground_truth": row["ground_truth"]
            })
        
        dataset = Dataset.from_list(results)
        
        # 2. Calculer les métriques RAGAS
        scores = evaluate(dataset, metrics=self.metrics)
        
        # 3. Vérifier les seuils (gate check)
        passed = True
        failing = []
        for metric, threshold in self.thresholds.items():
            if scores[metric] < threshold:
                passed = False
                failing.append(f"{metric}: {scores[metric]:.3f} < {threshold}")
        
        # 4. Rapport
        return {
            "scores": dict(scores),
            "passed": passed,
            "failing_metrics": failing,
            "ragas_score": scores.to_pandas()[list(scores.keys())].mean(axis=1).mean()
        }

# Utilisation dans un script CI
pipeline = RAGEvaluationPipeline(
    rag_system=my_rag,
    eval_dataset_path="eval_dataset.csv",
    thresholds={"faithfulness": 0.80, "answer_relevancy": 0.75,
                "context_recall": 0.70, "context_precision": 0.65}
)
result = pipeline.run()
if not result["passed"]:
    raise ValueError(f"Évaluation échouée : {result['failing_metrics']}")
    # → GitHub Actions échoue, déploiement bloqué

Erreurs fréquentes

❌ Erreur 1 — Évaluer sur les mêmes données que celles indexées (data leakage) ▼

Si les questions du dataset d'évaluation sont générées depuis les mêmes documents que ceux indexés, les scores sont artificiellement gonflés. Le système "connaît" les réponses car elles sont dans son index. Créer le dataset d'évaluation avant l'indexation, ou utiliser un sous-ensemble de documents distinct pour l'évaluation.

❌ Erreur 2 — Utiliser un seul score global pour diagnostiquer ▼

Un RAGAS score global de 0.72 ne dit rien sur où est le problème. Regarder toujours les 4 métriques individuellement : si Faithfulness = 0.95 et Context Recall = 0.50, le problème est le retrieval, pas la génération. Le score global masque l'information de diagnostic.

❌ Erreur 3 — Faire confiance aveuglément aux scores LLM-as-Judge ▼

Les LLM-juges ont des biais systématiques (verbosité, position, self-enhancement). Toujours calibrer l'évaluateur sur un petit jeu d'exemples annotés humainement. Mesurer la corrélation entre le LLM-juge et le jugement humain sur votre domaine spécifique avant de faire confiance aux scores automatiques.

❌ Erreur 4 — Dataset d'évaluation non représentatif ▼

Un dataset de 50 questions toutes simples et factuelles ne permet pas de détecter les problèmes sur les questions complexes ou multi-hop. Inclure une distribution représentative des types de questions réels : simples, complexes, ambiguës, hors-domaine. Analyser les logs utilisateurs pour comprendre la distribution réelle.

❌ Erreur 5 — Évaluer uniquement avant le déploiement, jamais en production ▼

Les performances peuvent se dégrader en production sans changement de code : évolution des questions utilisateurs, nouvelles données dans la base, drift du LLM (fine-tuning interne chez le provider). Sans monitoring continu, on peut passer des semaines à répondre avec un système dégradé sans le savoir.

Exercices

Facile Exercice 1 — Calculer la Faithfulness manuellement
Contexte : "Le SMIC horaire est de 11,65€ depuis le 1er mai 2023. Pour un temps plein (35h/semaine), le SMIC mensuel brut est de 1767€."

Réponse du LLM : "Le SMIC mensuel est de 1767€ brut. Avec 13ème mois, cela représente environ 1922€/mois en moyenne. Pour un 28h/semaine, le SMIC serait de 1414€."

Décomposez en affirmations et calculez la Faithfulness.
Décomposition des affirmations :
A1 : "SMIC mensuel est de 1767€ brut" → SUPPORTÉE ✅ (dans le contexte)
A2 : "Avec 13ème mois, environ 1922€/mois en moyenne" → NON SUPPORTÉE ❌ (inventé)
A3 : "Pour 28h/semaine, SMIC de 1414€" → PARTIELLEMENT supportée (le taux horaire est dans le contexte, mais le calcul pour 28h n'y est pas explicitement) → NON SUPPORTÉE directement ❌

Faithfulness = 1/3 = 0.33

La réponse a une très faible fidélité malgré son aspect plausible. Le 13ème mois et le calcul 28h sont des hallucinations (non mentionnés dans les sources).
Facile Exercice 2 — Diagnostiquer depuis les scores RAGAS
Voici les scores RAGAS de 3 systèmes RAG testés :

Système A : Faithfulness=0.92, Answer_Rel=0.88, Context_Recall=0.45, Context_Precision=0.78
Système B : Faithfulness=0.51, Answer_Rel=0.84, Context_Recall=0.88, Context_Precision=0.73
Système C : Faithfulness=0.85, Answer_Rel=0.79, Context_Recall=0.82, Context_Precision=0.38

Pour chaque système, identifiez le problème principal et proposez une action corrective.
Système A : Faible Context_Recall (0.45). La génération et la précision sont bonnes, mais le retrieval ne ramène pas tous les documents nécessaires. → Améliorer le chunking (semantic chunking, parent-document retrieval), augmenter K, ou utiliser le Hybrid Search pour capturer plus de documents pertinents.

Système B : Faible Faithfulness (0.51). Le retrieval est excellent mais le LLM invente des informations non présentes dans les documents. → Améliorer le prompt système (instructions strictes : "répondre uniquement depuis les documents"), ou utiliser un modèle de génération plus fiable avec température=0.

Système C : Faible Context_Precision (0.38). Le retrieval récupère les informations nécessaires mais aussi beaucoup de bruit. → Réduire K, ajouter un Cross-Encoder pour re-ranker, ou améliorer le filtrage par métadonnées pour réduire les faux positifs.
Moyen Exercice 3 — Concevoir un dataset d'évaluation
Vous développez un assistant RAG pour un service de support client d'un opérateur télécom. Les utilisateurs posent des questions sur leurs forfaits, factures, couverture réseau et problèmes techniques.

a) Combien de questions recommandez-vous pour le dataset initial ? Quelle distribution par type ?
b) Proposez 2 exemples de questions pour chaque type (factuelle, conditionnelle, multi-documents, hors-domaine).
c) Quelles métadonnées inclueriez-vous avec chaque paire (question, ground_truth) ?
d) Quelle stratégie de mise à jour du dataset au fil du temps ?
a) Dataset : 150-200 questions pour démarrer. Distribution : 40% factuelle (60-80Q), 25% conditionnelle (38-50Q), 20% multi-documents (30-40Q), 10% raisonnement (15-20Q), 5% hors-domaine (8-10Q).

b) Exemples :
Factuelle : "Quel est le prix du forfait 100Go ?" / "Combien de numéros puis-je appeler en illimité ?"
Conditionnelle : "Si j'ai consommé 95% de mes données, est-il possible d'en racheter ?" / "Quel est le délai de résiliation si je suis engagé ?"
Multi-documents : "Compare les forfaits 50Go et 100Go sur 5 critères" / "Quelles options sont disponibles en 5G vs 4G ?"
Hors-domaine : "Quel est le meilleur opérateur au monde ?" / "Conseille-moi un smartphone"

c) Métadonnées : {categorie: "forfait|facturation|reseau|technique|hors-domaine", difficulte: "simple|conditionnelle|multi-doc|reasoning", langue: "fr", date_creation: "2024-01-15", annotateur: "expert_id", version_docs: "v2.3"}

d) Mise à jour : Revue mensuelle des logs utilisateurs pour identifier de nouveaux types de questions non couverts. Ajouter 20-30 nouvelles questions/mois basées sur les cas réels. Re-évaluer le dataset complet quand les documents de référence changent (nouveaux forfaits, etc.).
Difficile Exercice 4 — Pipeline d'évaluation complet
Vous êtes responsable de la qualité d'un système RAG médical utilisé par 500 médecins pour consulter des protocoles de traitement. Le système génère ~10 000 réponses par jour.

a) Définissez vos seuils RAGAS minimum acceptables et justifiez-les (le domaine médical est critique).
b) Quelle stratégie d'évaluation proposez-vous (évaluation automatique vs humaine, fréquence, sampling) ?
c) Comment détectez-vous un cas de réponse "dangereuse" (hallucination médicale critique) rapidement ?
d) Quelle action prenez-vous si Faithfulness chute soudainement de 0.92 à 0.71 en 24h ?
a) Seuils médicaux stricts :
Faithfulness ≥ 0.95 (tolérance quasi-nulle aux hallucinations — conséquences potentiellement fatales)
Answer Relevance ≥ 0.90 (les réponses hors-sujet peuvent induire en erreur)
Context Recall ≥ 0.85 (un protocole manquant peut mener à un sous-traitement)
Context Precision ≥ 0.80 (le bruit peut diluer l'information critique)

b) Stratégie d'évaluation :
Automatique (LLM-as-Judge) : 100% des requêtes en temps réel pour Faithfulness uniquement (latence critique). Métriques complètes sur 20% en sampling horaire.
Humaine : 50 questions/semaine évaluées par des médecins experts. 100% des cas signalés par les utilisateurs. Review complète mensuelle du dataset (150 questions).

c) Détection hallucination critique :
Score de confiance factuelle spécifique : vérifier que toute posologie, toute contre-indication ou toute information médicale chiffrée est exactement supportée (pas approximativement). Ajouter une métrique custom "Medical Hallucination" qui pénalise spécifiquement les informations chiffrées non supportées. Alerting en temps réel si faithfulness < 0.85 sur une fenêtre de 10 questions consécutives.

d) Action si chute Faithfulness 0.92 → 0.71 :
1. Alerter immédiatement l'équipe de garde (PagerDuty)
2. Mettre le système en mode dégradé : afficher un avertissement aux médecins ("Vérifiez impérativement les sources indiquées")
3. Investiguer : changement de LLM provider ? Nouveaux documents ajoutés ? Dérive de la distribution des questions ?
4. Si cause non identifiée sous 1h : rollback vers la version précédente du système
5. Post-mortem pour identifier la cause racine

Quiz d'auto-évaluation

Q1. Quelle métrique RAGAS ne nécessite PAS de ground truth ?
A) Context Recall
B) Context Precision
C) Faithfulness
D) Aucune — toutes nécessitent un ground truth
Faithfulness (answer + contexts) et Answer Relevance (question + answer) ne nécessitent pas de ground truth. Context Recall et Context Precision le nécessitent pour comparer avec la réponse de référence.
Q2. Un système obtient Faithfulness=0.95 et Context Recall=0.40. Quel est le problème ?
A) Le LLM hallucine trop
B) Le retrieval ne récupère pas tous les documents nécessaires
C) Le contexte contient trop de bruit
D) La réponse n'est pas pertinente
Faithfulness haute → le LLM ne hallucine pas. Context Recall bas → le retrieval ne ramène pas tous les documents nécessaires pour couvrir le ground truth. C'est un problème de retrieval (chunking, index, K trop petit) — pas de génération.
Q3. Comment RAGAS calcule-t-il l'Answer Relevance ?
A) En comparant la réponse au ground truth mot à mot
B) En générant des questions inverses depuis la réponse et en mesurant leur similarité avec la question originale
C) En comptant les mots-clés en commun entre question et réponse
D) En demandant à un humain de noter de 1 à 5
RAGAS utilise un LLM pour générer N questions auxquelles la réponse pourrait répondre, puis calcule la similarité cosinus entre ces questions générées et la question originale. Si les questions générées sont proches de la question originale, la réponse est pertinente.
Q4. Quel biais du LLM-as-Judge est le plus documenté ?
A) Le biais de verbosité — préférence pour les réponses longues
B) Le biais linguistique — préférence pour le français
C) Le biais de date — préférence pour les réponses récentes
D) Le biais de format — préférence pour les listes à puces
Le biais de verbosité est le plus documenté : les LLMs-juges préfèrent systématiquement les réponses plus longues, même quand la réponse courte et précise est objectivement meilleure. Contre-mesures : évaluer la concision explicitement, ou utiliser des critères standardisés qui pénalisent la verbosité inutile.
Q5. Quelle est la meilleure stratégie pour un dataset d'évaluation de haute qualité ?
A) Générer 10 000 questions automatiquement avec un LLM
B) Utiliser uniquement des questions hors-domaine pour tester la robustesse
C) Combiner annotation humaine (Gold Standard 100-200Q) + génération synthétique pour la couverture
D) Évaluer uniquement avec le feedback thumbs up/down des utilisateurs
L'approche hybride est optimale : un petit set Gold Standard (100-200Q annotées par des experts) sert de référence absolute, complété par des questions synthétiques générées automatiquement pour couvrir plus de cas, et calibré par les vraies questions utilisateurs des logs de production.

Résumé du chapitre

🎯 Ce qu'il faut absolument retenir

1
L'évaluation RAG est multidimensionnelle : fidélité, pertinence, recall du contexte, précision du contexte. Un seul score ne suffit pas.
2
Faithfulness = anti-hallucination. Proportion d'affirmations supportées par les sources. Ne nécessite pas de ground truth.
3
Answer Relevance = pertinence de la réponse. Calculée via questions inverses + similarité vectorielle. Ne nécessite pas de ground truth.
4
Context Recall = couverture du retrieval. Le contexte couvre-t-il tout le ground truth ? Nécessite un ground truth.
5
Context Precision = rapport signal/bruit. Les docs récupérés sont-ils tous pertinents ? Nécessite un ground truth.
6
Le LLM-as-Judge corrèle à ~0.85 avec le jugement humain. Utiliser GPT-4 ou Claude Opus pour l'évaluation. Attention aux biais (verbosité, position, self-enhancement).
7
Le dataset d'évaluation est l'actif le plus précieux. Combiner Gold Standard annotés (100-200Q) + génération synthétique + logs utilisateurs.
8
L'évaluation doit être continue : avant déploiement (CI/CD gate) ET en production (monitoring, sampling). RAGAS, TruLens, DeepEval, LangSmith sont les outils de référence.
